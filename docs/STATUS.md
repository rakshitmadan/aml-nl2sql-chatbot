## What the database actually contains

Generated by `db/seed.py` with `random.seed(42)` / `Faker.seed(42)`, so
re-running it reproduces the same structure every time:

- 150 `customers`, 227 `accounts` (1-2 per customer)
- 120 `counterparties` — 7 flagged `is_sanctioned`, 9 flagged `is_pep`
- Matching `sanctions_list` (7 rows) and `pep_list` (9 rows) entries
- 2,863 `transactions`, made up of:
  - 2,800 ordinary "noise" transactions ($20-$8,000, random dates over ~6 months)
  - **8 structuring sequences** — 3-4 transactions of $9,000-$9,900 within a
    48h window on the same account (classic "smurfing," staying just under
    the $10k reporting threshold)
  - **10 large transactions** over $10,000 (straight CTR threshold breaches)
  - **6 transactions with sanctioned counterparties**
  - **1 velocity spike** — one account making 18 transactions in 3 days,
    against its own otherwise-quiet baseline
- 40 historical `alerts`, 15 `sar_filings` (pre-existing records, separate
  from the live rule engine we'll build in Phase 4)

**Verified** with `tests/verify_seed.py` (plain SQL + a pandas rolling-window
check) — every planted pattern is confirmed findable:

| Check | Found |
|---|---|
| CTR breaches (> $10,000) | 13 (10 planted + 3 incidental overlap from sanctioned-counterparty transactions) |
| Sanctioned counterparty transactions | 6 |
| Structuring (3+ txns $9k-$9,999, same account, within 48h) | 8 accounts |
| True velocity spike (≥15 txns in any rolling 3-day window) | 1 account |

One real bug was caught and fixed during verification: an early version of
the velocity check counted *lifetime* transactions per account instead of a
true rolling time window, which produced false positives from ordinary
random variance. Fixed by sliding an actual 3-day window across each
account's sorted transaction timestamps. Details in
[02-seed-data-and-verification.md](02-seed-data-and-verification.md).

## Phase 2 results

Tested against three real questions (see
[03-phase2-nl2sql-prototype.md](03-phase2-nl2sql-prototype.md) for full
detail):

- **CTR-threshold question** — correctly used SQLite date functions for
  "last month" rather than a hardcoded date, and filtered on `amount > 10000`.
- **"...tell me which are suspicious"** — the model correctly did *not* try

## Phase 3 results

Wrapped the prototype in an actual LangGraph `StateGraph` (3 nodes: generate
→ validate → execute) with a bounded repair loop. Full detail in
[04-phase3-langgraph-guardrail.md](04-phase3-langgraph-guardrail.md).

- The guardrail (`app/guardrail.py`) blocks non-SELECT statements, stacked
  queries, and hallucinated tables/columns — checked against the real
  schema pulled from `db/models.py`, not a second hand-written list.
- **A real bug was caught and fixed**: the first version relied entirely on
  `sqlglot`'s `qualify()` to catch bad table/column references, but
  `qualify()` doesn't flag a hallucinated table when the query is
  `SELECT *` (nothing to resolve columns against). Fixed with an explicit
  table-existence check run before `qualify()`.
- The repair loop was tested with a mocked LLM (the real model won't
  reliably produce broken SQL on command) — confirmed it recovers after one
  bad attempt and gives up cleanly after `MAX_RETRIES` (2) is exceeded.
- The query timeout guard was confirmed to actually fire, by forcing a
  0-second deadline against a real cross-join query.
- Real end-to-end test: "which counterparties are sanctioned" → correct SQL,
  correct 7 rows, first attempt.

## Phase 4 results

Built five deterministic rules (`app/policy_engine.py`, no LLM anywhere in
the file) and tested them against Phase 1's known ground truth. Full detail
in [05-phase4-policy-engine.md](05-phase4-policy-engine.md).

- **A real bug was caught, this time in Phase 1's data, not Phase 4's
  code**: running the rules over the full seeded database found the
  `high_risk_jurisdiction` and `pep_match` rules firing on 28% and 8% of
  *all* transactions — technically correct given the rule definitions, but
  useless as an alert signal. Root cause: counterparty country/PEP status
  had been assigned uniformly at random back in Phase 1, with no
  relationship to actual behavior. Fixed by having ordinary transactions
  touch elevated-risk counterparties at a realistic ~8% base rate instead of
  the ~27% that fell out of uniform random assignment. Re-verified Phase 1's
  own patterns still hold after the fix.
- `tests/test_policy_engine.py` locks in exact ground truth (CTR and
  sanctions transaction IDs, structuring/velocity account counts) plus a
  regression guard so jurisdiction/PEP rates can't silently creep back up.
- Current results: 12 CTR breaches, 6 sanctions matches, 28 structuring
  transactions across exactly 8 accounts, 18 velocity-spike transactions on
  exactly 1 account, ~7% jurisdiction rate, ~2% PEP rate.

## Integration: policy engine + Response Synthesizer wired into the graph

Full detail in [06-integration-policy-engine-synthesizer.md](06-integration-policy-engine-synthesizer.md).
The graph gained two nodes after `execute_sql`: `policy_engine` (re-queries
the DB by `transaction_id` rather than trusting the executor's raw
columns — the NL→SQL generator's column aliases aren't consistent enough to
rely on directly) and `synthesize_response` (turns findings into plain
English, constrained to only cite real numbers).

- **A real bug was found and fixed**: the Phase 3 guardrail's `LIMIT 500`
  was silently truncating results *before the policy engine ever saw them*
  — a real query for "last month" had 551 matching transactions, not 500,
  and with no `ORDER BY` the dropped 51 were arbitrary. Worst-case failure
  mode for a compliance tool: not a wrong flag, a missed one. Fixed by
  raising the cap to 5,000 (large enough not to truncate this project's
  realistic query volumes) and adding explicit truncation detection —
  `synthesize_response_node` now tells the analyst outright when results
  may be incomplete rather than silently presenting a partial view as
  complete.
- Real end-to-end test of the original ask — *"show me last month's
  transactions and tell me which are suspicious"* — now returns all 551
  real rows, 113 policy findings, and a complete, severity-organized,
  natural-language answer citing real transaction IDs, matching Phase 1/4
  ground truth exactly (8 structuring accounts, the known velocity-spike
  account, etc.).
- `tests/test_graph_integration.py` covers the two new nodes with mocked
  LLM calls (no API cost): correct no-op on non-transaction queries,
  correct scoping to returned transaction IDs, and correct
  presence/absence of the truncation warning.

**The chatbot can now do what the original ask described.**

## Phase 5 results

Full detail in [07-phase5-schema-rag.md](07-phase5-schema-rag.md). Replaced
the full 8-table schema dump with a `retrieve_schema` node (now the graph's
entry point) that embeds the question and retrieves only the top-5 most
relevant table descriptions, using Chroma's default local embedding model
(no extra API key needed).

- **A retrieval-quality bug was caught before it ever reached the graph**:
  tested the retriever standalone first, and `counterparties` — essential
  for judging suspicion (`is_pep`, `is_sanctioned`, `country`) — never
  ranked in the top 5 (or even top 6 of 8) for the flagship "which are
  suspicious" question. MiniLM's embedding favored `sar_filings` because
  its description literally contains the word "Suspicious," a classic
  lexical-overlap trap. Fixed by enriching table descriptions with
  representative question phrasings (standard RAG "document expansion").
- `tests/test_schema_rag.py` locks in the fix as a regression guard.
- Real end-to-end re-test with retrieval wired in: same 551-row, 113-finding
  result as the full-schema version — confirmed retrieval cost no accuracy.
- Honest limitation: at only 8 tables the token savings are modest — the
  value here is the *mechanism* being in place and tested, which is what
  would actually matter at real-bank schema scale (hundreds of tables).

## Phase 6 results

Full detail in [08-phase6-conversation-memory.md](08-phase6-conversation-memory.md).
Added a `chat_history` field (accumulates via LangGraph's `operator.add`
reducer instead of overwriting), a `record_history_node`, and
`build_graph(use_checkpointer=True)` using LangGraph's `MemorySaver`. New
interactive REPL: `app/chat.py`.

- **Two more real bugs, both caught only by running an actual two-turn
  conversation**:
  1. The LLM's own generated SQL for a structuring question grouped by
     `DATE(txn_date)` instead of `account_id` alone — approximating "within
     a time window" as "same calendar day," which misses clusters spanning
     midnight. Found only 3 of the known 8 accounts. Same category of
     mistake as Phase 1's own naive velocity-check bug, this time made by
     the model — fixed with an explicit prompt rule against exactly this
     approximation. Re-tested: all 8 accounts found correctly.
  2. The Phase 4-integration truncation warning false-positived on a
     deliberate small `LIMIT` — a follow-up "which one had the most"
     question correctly produced `LIMIT 1`, which the truncation heuristic
     misread as hitting the guardrail's safety cap. Fixed by comparing
     specifically against the guardrail's own default (`ROW_LIMIT`), not
     any limit value.
- `tests/test_chat_memory.py` (mocked, no API cost): history accumulates
  correctly across turns on one thread, stays isolated across different
  threads, and only gets injected into the prompt on follow-up turns.
- Real end-to-end two-turn conversation confirmed: turn 2 ("which of those
  accounts had the most transactions in its cluster?") correctly resolved
  "those accounts" to the exact 8 account IDs from turn 1, with no false
  warnings.

## Phase 7 results

Full detail in [09-phase7-streamlit-ui.md](09-phase7-streamlit-ui.md).
Built [`app/streamlit_app.py`](../app/streamlit_app.py) — chat UI,
per-session `thread_id` (so Phase 6 memory works through the browser, not
just scripted tests), and a "Query details" expander under every answer
showing retrieved tables, exact SQL, and finding counts.

- Hit and worked around a real environment quirk: the browser preview
  tool's process is sandboxed to a sibling project directory and can't
  reach this project's venv. Worked around by launching Streamlit directly
  and pointing the preview at its URL instead of having the sandboxed
  process launch it.
- **The most important bug of the whole project was caught here, and only
  here**: clicking through the *actual running UI* (not a scripted
  question) with "which accounts show signs of structuring or smurfing"
  produced an answer claiming *"the policy engine did not flag these...gap
  in the automated ruleset."* False — the query was aggregated (`GROUP BY`
  + `GROUP_CONCAT(transaction_id)`), so the policy engine correctly never
  ran on it at all; the synthesizer just had no way to know that and
  invented a confident, wrong explanation instead. Fixed by having
  `policy_engine_node` explain itself via a new `policy_engine_note` field
  whenever it skips analysis, and instructing the synthesizer to relay
  that honestly rather than speculate. Five passing automated test suites
  at this point had not caught it — the bug was in what the model *chose
  to say* about a correctly-handled state, only visible by reading a real
  generated answer.
- Regression-tested in `tests/test_graph_integration.py`; re-verified fixed
  both via direct script and by re-clicking through the live browser UI.

## The full plan we're following (all 7 phases)

Copied here from the original architecture note for reference:

1. **Synthetic DB + seed data generator** ✅ done
2. **Single-shot NL2SQL** with hardcoded schema in prompt, no graph yet ✅ done
3. **Wrap in LangGraph** ✅ done. Guardrail node (read-only DB role, keyword
   blocklist, row limits, table/column allowlist) and an executor node
4. **AML Policy Engine** ✅ done, tested, and wired into the graph (plus a
   Response Synthesizer, which the original plan folded into this phase
   implicitly via the full graph diagram below). Deliberately *not* an LLM
   call. Plain Python functions implementing: CTR threshold check,
   structuring/smurfing detection, velocity checks, sanctions/PEP list
   matching, high-risk jurisdiction flags. Each rule returns a structured
   finding (`{transaction_id, rule_triggered, severity, explanation}`).
   Tested independently of the LLM.
5. **Schema RAG** ✅ done. Embeds table/column descriptions (Chroma, local
   embeddings) and retrieves only the relevant subset per question.
6. **Conversation memory** ✅ done. LangGraph `MemorySaver` checkpointer so
   follow-ups like "tell me more about that one" work across turns.
7. **Streamlit front end** ✅ done. Minimal chat UI, memory-aware, with a
   query-details transparency panel.

Full graph shape (from the original design):

```
START
  │
  ▼
[Intent Classifier] ──► routes to: sql_query | clarify | out_of_scope
  │
  ▼
[Schema Retriever]  (RAG over table/column metadata, not full schema dump)
  │
  ▼
[NL → SQL Generator]
  │
  ▼
[SQL Guardrail / Validator]  ──► fails? ──► [Repair Loop] (max 2 retries) ──► back to Generator
  │ passes
  ▼
[SQL Executor] (read-only DB role)
  │
  ▼
[AML Policy Engine]  (deterministic Python, NOT the LLM)
  │
  ▼
[Response Synthesizer]  (LLM turns structured findings → natural language)
  │
  ▼
END (state checkpointed for multi-turn follow-ups)
```

State carried through the graph (a `TypedDict`): `user_query`,
`chat_history`, `retrieved_schema`, `generated_sql`, `validation_errors`,
`query_results`, `policy_findings`, `final_answer`.
